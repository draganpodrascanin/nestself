# Auth Phase 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish the authorization half of the auth feature: step-up enforced, grants administered from the apps, operations routes for assigned clients, the confidential domain and emergency access, legacy roles backfilled, and the review gaps from `docs/auth/implementation.md` §21 closed.

**Architecture:** Everything builds on the phase 1 pieces that already exist: the pure `authorize()` engine and `ContextLoader`, `AuthorizationGuard`, `SessionService.markStepUp/regenerate`, `ChallengeStore`, the Drizzle schema with forced row-level security, `AuditWriter`, `MaintenanceJobsService` plus the BullMQ scheduler, and the `@nestself/contracts` schemas that already describe grants, approval authorities and step-up. New NestJS modules (`grants`, `professional`, `emergency`) follow the `members` module layout: controller with `@Authorize(action, resolver)` + `ZodValidationPipe`, service running inside `DbService.withOrgScope`, repository methods on `AuthorizationRepository`, audit per write, principal invalidation after grant changes. The web apps get an `org-admin` api-client module, a step-up dialog wired into the existing `stepUp` placeholder, and one access-management screen each.

**Tech Stack:** NestJS 12, Drizzle ORM 0.45 + drizzle-kit, PostgreSQL 17 RLS, Redis via `KeyValueStore`, BullMQ 6, Zod, Vitest, supertest e2e (needs `TEST_DATABASE_URL`), React 19 + TanStack Router/Query, `@nestself/ui`, i18next, Playwright.

**Spec:** `docs/tasks/auth/phase-2-readiness.md` (ordered work list and decisions) and `docs/tasks/auth/auth-strategy.md` §3.6.9, §4.5.6, §4.7, §4.8, §5.3, §5.4, §9.5 (tasks T-2.x). Executors read both.

## Decisions taken for this plan (not in the spec)

| Decision | Why |
| --- | --- |
| Step-up method is **email OTP for every native user**, including `password_totp` users and the `emergency` class | Cognito's USER_AUTH flow cannot issue a SOFTWARE_TOKEN_MFA challenge without a password first, so an authenticator-only step-up would mean re-entering the password. The strategy allows email OTP for every class except `emergency`; that deviation is recorded in `implementation.md` §21 and listed for the owner. |
| `restricted` class is enforced as a plain max-age (15 min since `max(auth.time, lastStepUpAt)`), not "first access per session" | Same code path as the other classes; the stricter reading can be added later without a contract change. |
| Grant-write throttle (10/min) uses the existing `default` throttler keyed by IP | No named throttler or session tracker exists; adding one is a one-line follow-up noted in §21. |
| T-2.7 drops `users.platform_role` and `memberships.role` only. `memberships.team_id`, `legacy_teams` and the community tables stay | Those belong to the community feature retirement, not to auth; the API reads none of them. Contract `OrgRole`/`PlatformRole` stay for sample mode (D-36). |
| Confidential-domain tables are placeholders with the minimum columns; reads go through `AuthorizationService.require()` after the row is loaded | The resource needs row data (`caseId`, `ownerId`, `orgId`) that a static `@Authorize` resolver cannot load. |
| Not in this plan: T-2.8 (needs staging), T-2.9 and T-2.11 (no files or exports exist to authorize), T-2.12 and the retention sweeper (need S3 and owner decisions L-02/L-03), mobile step-up UI (mobile has no step-up action yet), phase 3 SSO (separate plan after this one) | Stated in the readiness doc; nothing to build against. |

- Audit `details` never contain keys named `password`, `code`, `token(s)`, `secret`.
- Commit after every task with the attribution trailer `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.
- DB-backed suites need `TEST_DATABASE_URL=postgresql://nestself@localhost:54329/nestself_test` (local PostgreSQL 17, superuser `nestself`); use a new suffix per suite.

## Review Focus

1. **Session principal with `lastStepUpAt` older than `auth.time`** (user re-signed in after an old step-up): freshness must use `max(auth.time, lastStepUpAt)`, never `lastStepUpAt` alone. Test in Task 2.
2. **Step-up challenge consumed by another user's token**: a step-up challenge token presented under a different session must fail with `invalid_challenge` and not mark the second session as stepped up. Test in Task 2.
3. **Delegation to a user outside the organization or deeper than 3**: must return 403 `delegation_exceeds_boundary`, not 500 and not a created grant. Test in Task 5.
4. **Emergency access approved then expired between two requests**: the second read is denied by `authorize()` even before the 15-minute sweeper runs. Test in Task 8.
5. **Wrong email code retried with the same challenge token**: the challenge survives up to three wrong codes and the correct code then succeeds; the fourth wrong code ends it. Test in Task 11.
