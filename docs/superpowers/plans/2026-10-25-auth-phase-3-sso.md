# Auth Phase 3: Enterprise SSO Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An employer's SAML or OIDC identity provider can be registered, verified, tested and activated by staff; employees of that employer sign in through it (home-realm discovery, PKCE code flow through Cognito, identity resolution per D-04) in both web apps and the API; everything is testable locally against the fake identity provider, with the live IdP test (T-3.4) left for the pilot employer.

**Architecture:** Extends the phase 1/2 pieces: `IdentityProviderService` gains provider-management and code-exchange methods (Cognito adapter + in-memory fake); a new `sso` NestJS module owns `sso_connections`/`sso_domains` (repository, service, controller under `/ops/sso-connections`); `DiscoverService` performs home-realm discovery; `/auth/sso/start` and `/auth/sso/callback` live in a new `SsoCallbackService` that reuses `IdentityResolutionService`, `InvitationsRepository` and `SessionService`. Admin app gets an SSO connections page. A nightly job watches certificate expiry. The CDK task role gains the Cognito provider IAM actions.

**Tech Stack:** as phase 2. ID-token verification: use `aws-jwt-verify` only if it is already in `node_modules` (no installs); otherwise verify RS256 against the pool JWKS with Node `crypto` (`createPublicKey({ key: jwk, format: 'jwk' })`, `crypto.verify`), caching the JWKS per `kid`.

**Spec:** `docs/tasks/auth/auth-strategy.md` §3.4 (3.4.1–3.4.10), §3.6 "SSO redirect", §5.1 rows `GET /auth/sso/start|callback` + API-R-06/07, §5.4 SSO rows + zod sketch (L3090–3128), §9.6 (T-3.1–T-3.3), §10.1 runbook, D-03, D-04, D-12. Existing groundwork: `ssoConnections`/`ssoDomains` tables, `pkceKey`, `samlAssertionKey`, `hasSsoForEmailDomain`, web `sso` screen redirect, mobile PKCE hook (`apps/mobile/src/auth/sso.ts`), CDK callback URLs `/api/auth/sso/callback`.

## Decisions taken for this plan

| Decision | Why |
| --- | --- |
| `DiscoverResponseSchema` keeps `{ method, ssoStartUrl, connection }`; `ssoStartUrl` is an absolute URL built from `API_PUBLIC_URL` (fallback: the request's origin) so `.url()` holds; `connection` = `cognitoProviderName` (mobile uses it as `identity_provider`) | The strategy's `connectionId/startUrl` naming never shipped; both clients already consume the current shape |
| SP-initiated only. `idpInitiatedAllowed` stays `false` and `PATCH` refuses `true` with 422 `validation` until the risk-acceptance process exists; the `saml_assertion:{id}` replay cache is therefore not wired | SSO-R-12; nothing in the code flow needs it |
| Unverified assertion email (SSO-R-08 fails) → the callback redirects to the surface's `/sign-in?reason=sso_email_unverified` and the user continues with the email code flow; no binding | Strategy step 4; the email-OTP flow already exists |
| Registering a provider also adds it to the web client's `SupportedIdentityProviders` (and the mobile client's) via `UpdateUserPoolClient`, preserving `COGNITO` | Cognito refuses `identity_provider=<name>` on `/oauth2/authorize` unless the client lists it |
| DNS verification: resolve the domain's NS records, query one authoritative server directly for `TXT _nestself-verify.<domain>`; compare with `timingSafeEqual`; the resolver is an injectable `DnsTxtResolver` so tests use a fake | SSO-R-06 |
| Fake IdP in stub mode: `FakeIdentityProvider` keeps providers in memory and exposes a stub-only `GET /auth/sso/_fake/authorize` that immediately redirects to the callback with a code for a seeded federated user | Lets every resolution path run in e2e and Playwright without a real IdP |
| Certificate-expiry job logs and audits; the SES email goes with the SES mailer follow-up | `SES_OPS_ALERT_EMAIL` does not exist yet |
| Staging/production Cognito custom domain remains a CDK follow-up (`addDomain` for `auth.<domain>`); the SP metadata the runbook hands to the client uses the stage's `cognitoDomain` output | Out of this plan; dev uses the prefix domain |

## Global Constraints

Same as `2026-10-24-auth-phase-2.md` (no installs; every route `@Public/@Authenticated/@Authorize`; RLS + FORCE on tenant tables; audit details sanitised, never tokens/codes/assertions; failures visible with translated copy; four locales with generated `sr-Cyrl`; sample data rules; commit trailer `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`; DB suites with `TEST_DATABASE_URL`; API suite suffixes unique: `sso`, `ssoauth`). SSO-R-04: `POST /auth/discover` keeps the same shape, status and timing (within the existing `neutralDelay`) for every input. SSO-R-09: email comparisons lowercased, trimmed, timing-safe. SSO-R-10: denied binding deletes the orphan Cognito user and shows a neutral screen.

## Review Focus

1. **Callback with a `state` that was already consumed or never issued** → neutral redirect to the surface error path, no session, nothing logged beyond an audit `auth.sign_in.failed`. Test in Task 4.
2. **Assertion email that matches a pending invitation of a different organization than the connection's** → no binding (invitation must belong to the connection's org). Test in Task 4.
3. **Verified domain already attached to another connection** → 409 on add; `domain` unique. Test in Task 3.
4. **Connection `SUSPENDED` while an employee is mid-flow** → callback still resolves an existing external identity (session creation does not depend on status) but discover routes new sign-ins to the native method. Test in Task 4.
5. **Provider name collision or >20 chars** (`org-<slug>-saml`) → 422 at create, with the slug truncated deterministically and uniqueness checked against `cognito_provider_name`. Test in Task 3.
