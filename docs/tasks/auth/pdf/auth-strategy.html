Overview

What this strategy decides

Thirteen of the thirty-six decisions carry the design. Every decision has a numbered entry, with conditions and dissent, in the engineering reference.

Cognito authenticates everyone. NestSelf decides what each person may do, in its own database, through one decision function. Web apps hold a cookie, never a token. Employees never set a password.

D-01
One Cognito user pool per environment in Frankfurt, Essentials plan, for every population
Email codes, passkeys and token rotation come with the plan; ten thousand direct users are free; nothing leaves the EU.
D-02
No authorization data in tokens
Tokens prove who signed in. Memberships and grants live in PostgreSQL and are read, cached for seconds, on every request.
D-03
Invitation first; no self sign-up; linking of identities in NestSelf's database
HR stays the gate. One identity per person across employers; Cognito's account-linking API is not used.
D-05
Employees sign in with their employer's SSO or an emailed code; experts and staff with a password and an authenticator app
No passwords for the largest population, no SMS, a second factor wherever someone manages other people's data.
D-06
The API is the only OAuth client for the web apps and keeps sessions server-side
Browsers hold an httpOnly cookie. Revoking access means deleting one key.
D-07
The mobile app uses the standard native flow with tokens in the device keychain
Unanimous over a custom handoff: proven libraries, what auditors expect, weeks saved. Short tokens and per-request checks close the gap.
D-08
Each web app and its API share one origin behind CloudFront
Strictest cookie scope, no cross-origin requests, one cookie per surface.
D-11
NestSelf owns every sign-in screen, in Serbian, Hungarian and English
Cognito's hosted pages offer neither language; they appear only as a silent hop during SSO.
D-12
One SSO connection per employer, on verified email domains, started from NestSelf
Three hundred connections fit one pool. DNS verification stops domain hijacking; portal-initiated sign-in stays off by default.
D-15
Authorization is a grants model with one pure decision function
Default deny, explainable decisions, delegation envelopes, effective-access preview. Scored far above policy engines for this model.
D-20
Private case content is a separate domain with four doors and no administrator key
Participant, assigned expert, supervision grant or time-limited emergency access. Platform and support roles are refused in code.
D-24
ECS Fargate, RDS PostgreSQL, ElastiCache Valkey, S3 and CloudFront, all written as CDK founder: budget
Infrastructure two engineers can run. Multi-AZ database and managed NAT from the first paying client unless the founder chooses savings.
D-35
Five phases, about fifteen weeks to an SSO-ready pilot
Foundations and spikes, identity and sessions, authorization administration, first employer SSO, hardening. Compliance runs alongside.

Sign-in journeys

How employees sign in

Identifier-first: the email decides the route. The browser never receives a token, only a cookie that names a server-side session.

An employee of a client with single sign-on

Employee
Opens the workspace and types a work email on the NestSelf sign-in page, in their own language.
API
Finds a verified email domain with an active SSO connection, starts the authorization-code flow as Cognito's confidential client and redirects the browser straight to that identity provider.
Employer IdP
Authenticates the employee with the employer's own second factor and returns a signed assertion to Cognito. No Cognito screen is shown.
Cognito
Issues an authorization code to the API's callback address.
API
Exchanges the code, verifies the tokens, binds the identity to the pending invitation, creates the session and sets the httpOnly cookie.
Employee
Lands in the personal workspace. A manager also sees the switch to the organization context.

An employee of a client without an identity provider

Employee
Types a work or personal email address. No SSO connection matches the domain.
API
Shows the same next step whether or not the address is known, so nothing reveals who has an account, and asks Cognito to send a one-time code using NestSelf's localised email template.
Employee
Enters the code from the email. On the first visit the invitation link already carried the token that binds this identity to the membership.
API
Completes the Cognito challenge, creates the session, sets the cookie and records the sign-in method and time on the session for later step-up checks.
Employee
Lands in the workspace. A "remember this device" choice keeps the personal workspace signed in on that device; the organization context always asks again.

No passwords for employees

Email codes and employer SSO cover every employee. Nothing to forget, nothing to leak, nothing to migrate.

One page, four languages

Serbian Latin and Cyrillic, Hungarian and English. Cognito's pages offer none of the first three, so NestSelf owns every screen.

Neutral by design

Invitation and code emails never name a service category. Only the signed-in workspace shows what is available.

Sign-in journeys

Experts, staff and the mobile app

Higher trust means a password and an authenticator app. The phone follows the standard native flow.

An expert on the web

Expert
Types their email; the API answers that this identity signs in with a password.
API
Checks the password with Cognito on the server, receives a one-time-code challenge for the authenticator app and relays it. The browser never talks to Cognito.
Expert
Enters the six-digit code from the authenticator app enrolled at activation.
API
Completes the challenge, creates the session with its method and time recorded, sets the cookie. Staff sign in the same way in the admin app, with shorter sessions.

An employee of an SSO client on the phone

Employee
Types the work email in the app; the app learns that this domain uses the employer's identity provider.
App
Opens the system browser to Cognito with a one-time code challenge, naming the employer's provider. No screen is shown before the employer's own sign-in page.
Employer IdP
Authenticates the employee and returns to Cognito, which returns an authorization code to the app's registered link.
App
Exchanges the code with Cognito, stores the tokens in the device keychain and calls the API with a short-lived bearer token. Employees without SSO receive their emailed code inside the app instead.
API
Verifies the token's signature, resolves the person from the database, checks that the membership is still active and that the token family is not revoked, then decides.

What the browser never sees

Cognito tokens. The web apps hold one cookie that names a session in Valkey; signing out deletes it.

What the phone holds

Rotating Cognito tokens in secure storage, 15-minute access tokens, biometric gate for sensitive reads, discarded after 30 days unused.

How access ends

Ending a membership deletes sessions, revokes refresh tokens, disconnects live channels and denylists the phone's token family, within a second.

Enterprise SSO

Connecting an employer's identity provider

One connection per employer, registered by NestSelf operations. Employees never see a Cognito screen.

Two weeks, mostly waiting

The work on NestSelf's side is a few hours. The elapsed time is the client's IT queue: a DNS record, an identity-provider application and a test user.

NestSelf sends

  • Service-provider entity ID and the assertion consumer URL
  • Signing certificate
  • The attribute list: persistent NameID, email, given name, family name
  • A DNS verification token per email domain

The client sends

  • Metadata URL or XML (SAML) or issuer and client ID (OIDC)
  • The list of email domains employees use
  • A test account
  • Whether sign-in may start from their portal (off by default)

  1. Register the connection

    Operations create the connection in draft state: protocol, provider name, the organization it belongs to. Nothing routes to it yet.

  2. Verify the email domains

    The client publishes a DNS record with the token. Only verified domains take part in routing; public mail domains are refused.

  3. Exchange metadata and map attributes

    The provider is created in Cognito from the metadata. The persistent NameID identifies the person; email and names fill the profile. IdP groups are ignored: access comes from NestSelf grants.

  4. Test with one user

    The connection moves to testing. A test sign-in must produce a verified email, bind to an invitation and show the right names before anyone else is routed.

  5. Invite the roster

    HR imports the roster; each person receives a neutral invitation. If the client prefers, verified-domain sign-ins may create memberships automatically into a default unit.

  6. Go live and watch the certificate

    The connection becomes active. Cognito refreshes metadata within six hours; a reminder fires 30 days before the IdP certificate expires so rotation overlaps.

Authorization

One decision function, everywhere

authorize(principal, action, resource) is pure once its inputs are loaded, explains itself, and is the only path to a yes.

  1. Is the person active?

    Suspended or deactivated users are refused before anything else is read.

  2. Is the context valid?

    The organization context needs an active membership; expert and operations contexts need the matching capability.

  3. Is this restricted content?

    If so, only a participant, an assignment, a supervision grant or emergency access can allow it. Administrative grants are refused here, in code.

  4. Which grants match?

    Action and scope, with the organization tree resolved from the closure table; assignments cover queues, cases and clients.

  5. Do the conditions hold?

    Spending ceiling and currency, permitted categories, confidential approver, time window, validity dates.

  6. Is anyone approving themselves?

    Denied unless the organization documented otherwise; the router always finds an alternate.

  7. Explain the answer

    Allowed or denied, the grant ids that mattered, a reason, and a trace used by tests and the effective-access preview.

Decisions for the founder

What needs you

The document assumes the default in each card until you decide otherwise. None of them changes the architecture.

F-01 · Where NestSelf is incorporated

Sets the contract template, the supervisory authority and whether EU standard clauses sit in Hungarian client agreements.

Default: Serbian company; EU clauses, module two, for Hungarian clients.

F-02 · Professional notes on the platform

Clinical notes would pull in health-documentation law in both countries, with 15- and 30-year retention.

Default: not at pilot; scheduling metadata only. The restricted domain is built either way.

F-03 · Minimum reporting cohort

Below this size an employer report shows nothing. Smaller numbers raise re-identification risk.

Default: ten people per cell, confirmed with the data protection officer.

F-04 · English-only sign-in for a pilot client

Would save one to two weeks by using Cognito's hosted page, which has neither language.

Default: no; localised sign-in from day one.

F-05 · Pilot budget posture

Multi-AZ database and managed NAT, or single-zone and community NAT for about $90 a month less.

Default: production grade from the first paying client.

F-06 · Mobile token model

The panel was unanimous for the standard native flow; the custom variant is documented as rejected.

Default: standard native flow with tokens in the device keychain.

F-07 · Domain names

Placeholders are used for the site, the apps, the API and the sign-in domain.

Default: nestself.rs with app, admin, api and auth subdomains; registered in phase 0.

F-08 and F-09 · Staff identity provider; telling employees about emergency access

Staff could later sign in through a company workspace provider. Employees could be told, after the fact, when emergency access touched their records.

Defaults: Cognito with authenticator apps at pilot; yes, unless counsel objects.
